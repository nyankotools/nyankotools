# Development rules: coding conventions and commits

Rules to follow in day-to-day development. See [CLAUDE.md](../../CLAUDE.md) for the project-wide premises.

## Language

- Site copy is provided in both ja and en (dictionaries under `src/i18n/`). Commit messages and code comments are in Japanese (match the existing history).
- Identifiers (variable and function names, etc.) are in English.

## Coding style

- Lint: ESLint (`eslint.config.js`, flat config), combining `typescript-eslint` + `eslint-plugin-astro` + `eslint-config-prettier`.
- Format: Prettier (`.prettierrc.json`, with `prettier-plugin-astro`). `singleQuote: true`.
- Run `pnpm run lint` and `pnpm run format` before committing.
- Before `git commit`, run `pnpm exec prettier --check` on the staged files too (files written by subagents such as `tool-qa` have slipped through unformatted).
- `typescript` is pinned to `6.0.3` (`^6.0.3`) because `astro check` and `typescript-eslint` don't yet support the TypeScript 7 native (Go) compiler API. Don't bump to 7.x until both tools support it.
- Line endings are LF (the global standard). The root `.gitattributes` (`* text=auto eol=lf`) enforces this, so committed content is always LF even if Windows has `core.autocrlf=true`. Don't leave it to editor or OS defaults.

## Writing tool logic

- Write each tool's actual processing (parsing, conversion, calculation, etc.) in `src/lib/tools/<slug>.ts` as "plain, framework-free TypeScript functions".
- The page's `<script>` tag imports these functions and only updates the DOM. Never write logic directly in the page.
- The same rule applies to the markup (template section) of `.astro` pages: no `locale === 'ja'` branches for era names, date formats, units, etc. — use dictionary format templates with `fill`. The rule targets tool pages (their markup and scripts). Out of scope: frontmatter and libraries (`src/lib/*`, e.g. path-prefix helpers), and shell components that are not tool pages. Known exceptions: CronParser (Intl), LoremIpsum, the top page, `ShareButtons.astro`, the language-switch label in `Layout.astro`, the English label table in `CategoryPage.astro`, `UpdatesList.astro`. Move these into `src/i18n/ui.ts` when a third language is planned.
- Locale-specific text must not be branched in page scripts (no `isJa` / `lang === 'en'` / `numberLocale === 'ja-JP'` checks). Either put locale-aware sentence generation in `src/lib/tools/` as a pure function taking a `locale` argument (e.g. `cron-description.ts`, the kishu-izon data table), or put format templates in the i18n dictionary, pass them via `data-*`, and fill them with `fill` / `count` from `src/lib/format-template.ts` (e.g. age-calculator's `resultFormat`).
- When filling a template with a user-derived value (file name, pattern, error message that echoes input), use `fill` or pass a function replacer (`.replace('{name}', () => file.name)`). A plain string replacement interprets `$&` / `$'` / `` $` `` in the value. Static dictionary values and numbers can keep the plain form.
- Tests use Vitest (`pnpm test` / `pnpm run test:watch`). Target the pure logic in `src/lib/tools/*.ts`, not Astro pages (e.g. `src/lib/tools/char-counter.test.ts`).
- E2E tests that check real browser behavior (navigation, DOM updates, etc.) use Playwright (`pnpm run test:e2e` / `pnpm run test:e2e:ui`). Test files go in `e2e/*.spec.ts` at the repo root. The boilerplate checks common to all tools (sidebar navigation, 375px horizontal overflow, h1 display, in ja and en) are generated by `e2e/tools-common.spec.ts` from the `src/data/tools.ts` registry, so per-tool specs contain only tool-specific checks. The same spec also runs axe (`@axe-core/playwright`, WCAG 2.x A/AA) on every tool page in ja and en, so new UI must keep text contrast ≥ 4.5:1 (avoid `text-gray-400` on light backgrounds), give every form control a `<label for>`/`aria-label`, and give scrollable regions `tabindex="0"`. `src/data/registry-integrity.test.ts` (Vitest) checks registry/page/dictionary/FAQ consistency and title/description/h1 quality (length range, duplicates, near-duplicate descriptions), and `pnpm run check:bundle` (`scripts/bundle-budget.mjs`, run in CI after the build) fails when a page's gzip JS exceeds the budget (80KB normal, 520KB for `heavy` tools); raise a budget only when a heavy library is added on purpose. `webServer` in `playwright.config.ts` runs `pnpm build && pnpm preview --port 4322 --ignore-lock` automatically (`--ignore-lock` keeps Astro 7 from daemonizing the preview when it detects an AI agent, which Playwright would treat as "exited early"), so no server needs to be running beforehand. It deliberately serves the production build on a port separate from `pnpm dev` (4321): `astro dev` does not enforce the CSP (`security.csp` in `astro.config.mjs`), so tests against it would miss CSP violations. Any tool that loads wasm, fetches files, or uses new URL schemes must be verified against this built output, and CSP changes must be reflected in `e2e/csp-headers.spec.ts`. If the browser binary is missing before the first run, run `pnpm exec playwright install chromium`.
- To test an added/changed tool exhaustively, use the `/qa-test` command. An independent QA subagent (`.claude/agents/tool-qa.md`), separate from the implementing conversation, runs lint / type check / build / Vitest / Playwright, adds any missing tests itself, and reports the results.
- For code review, use the `/tool-review` command. An independent review subagent (`.claude/agents/tool-reviewer.md`) reports findings only (it doesn't change code), covering correctness, simplicity, convention compliance, static-site constraints, SEO/responsive, and security.

## Commit messages

- Write in Japanese, summarizing the change concisely (e.g. `wrangler.jsoncにbuild.commandを追加してデプロイ前ビルドを自動化`).
- Match the style of the existing `git log` (noun-phrase endings, 「〜を追加」「〜を修正」, etc.).

## Permission settings

`.claude/settings.json` currently auto-allows only the file read/write tools (Read/Edit/Write/MultiEdit/Glob/Grep). Shell commands such as git and pnpm are intentionally set to prompt every time; this is not an oversight. Ask the user before changing it.

## UI primitives

- Tool pages use the `ui-*` classes defined in `@layer components` of `src/styles/global.css` (`ui-btn`, `ui-input`, `ui-label`, etc.) so that design changes (radius, focus ring, tap area) happen in one place. Sizing (`h-11 w-24`) and background colors (`bg-*` / `dark:bg-*`) are set per element as utilities.
- Classes in the components layer always lose to utilities that set the same property, regardless of variants. That is why the primitives contain no background colors: a `dark:bg-*` inside a primitive would lose to a plain `bg-gray-50` on the element and break dark mode. Do not add properties to a primitive that elements commonly override with utilities.
