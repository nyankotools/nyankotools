# 01. 作業の流れと役割

## 基本の流れ

```
実装 → レビュー → QA → （ユーザーが確認・コミット指示）
```

- 順序を守る。**並行しない。**
- 各段階は「別の視点で見直す」ために分けている。**役割ごとに新しいセッション（opencode を起動し直す or 新規会話）で行う**のが理想。同じ会話の中で自分の実装を自分でレビューすると、見落としが増える。
- どうしても同じ会話で続ける場合は、レビュー・QA に入る前に「実装した側の説明を信用せず、コードそのものを読む」と自分に言い聞かせて、`git diff` から読み直す。

## 実装役

1. `02-add-tool-recipe.md`（新規）または該当ファイルを読み、参照実装を先に読む。
2. 小さな単位（1ファイル）ずつ作る。作るたびに型・lint を通す（`05-commands.md`）。
3. 完了したら `pnpm dev` を起動し、確認用 URL（http://localhost:4321）をユーザーに伝える。
4. **起動した開発サーバーは、ユーザーが止めてと言うまで終了しない。**
5. 実装が終わったら `handoff.md` を更新し、レビューへ進む。

## レビュー役（`03-review-checklist.md`）

- **コードもテストも変更しない。指摘のみ。**
- 重大指摘（バグ・セキュリティ・サーバー通信）が出たら、QA に進む前に実装役が直す。直さない場合はユーザーに報告して方針を聞く。
- 軽微な提案だけなら、そのまま QA に進んでよい。

## QA 役（`04-qa-checklist.md`）

- lint / 型チェック / ビルド / 単体テスト / E2E を実際に実行する。
- 不足しているテストは自分で追加する。実装のバグを見つけても、大きな修正はせず「失敗するテスト＋バグの内容」を報告する。

## コミットのルール

- **ユーザーが明示的に指示するまで `git commit` しない。** 実装が終わってもコミットせず、確認と指示を待つ。
- `git push`、ブランチ削除、`git reset --hard` など取り消しにくい操作も、指示なしでは実行しない。
- コミットメッセージは日本語で、既存履歴のスタイルに合わせる（例:「テキストケース変換ツールを追加」「〜を修正」）。

## ドキュメント更新のルール

- `memo/実装予定一覧.md` に載っている予定ツールを実装したら、該当行のチェックボックスにチェックを入れ、「実装済み」セクションへ移動する。サマリーの件数も更新する。あわせて `src/data/tools.ts` へ登録する。
- 各行の `No.xxx`（ツール固有の通し番号）は固定ID。移動しても変えない。新規ツールを一覧に足すときは最大番号の次を付け、`08-tool-numbers.md` の表にも追記する。ユーザーが番号で指示してきたときの手順も `08-tool-numbers.md` にある。
- `memo/` は git 管理外。更新してもコミット対象にならない。

## Claude Code との分担

- ローカルLLMと Claude Code が交代で作業する場合、`handoff.md` に「今のタスク・決めたこと・未完了・次にやること・触ったファイル」を書く。読む側はまず `handoff.md` を読む。
- 相手が実装した内容も、自分がレビュー・QA を担当するなら、実装者の説明を信用せずコードから読む。
