# 03. レビュー役のチェックリスト

## 役割

実装した側の説明を信用せず、**コードそのもの**を読んで評価する。**コードもテストも変更しない。指摘のみ行う。** テストの実行・追加は QA 役（`04-qa-checklist.md`）の担当。

## 禁止事項

- ファイルを書き換えない（Edit / Write を使わない）。
- **シェル経由でも書き換えない。** 過去に `prettier --check` のつもりで `--write` を実行する事故があった。次のものは使わない: `--write`、`--fix`、`sed -i`、`>` `>>` によるリダイレクト上書き。
- 実行してよいのは確認系のみ: `git status`、`git diff`、`git log`、`pnpm exec astro check`、`pnpm run lint`、`pnpm exec prettier --check .`。
- `git commit` しない。

## 対象の特定

1. `git status` と `git diff` で未コミット差分を見る。範囲や slug を指定されたらそれに従う。
2. 変更されたファイルを**全文**読む。差分だけでなく、呼び出し先の既存コードも必要に応じて読む。

## 観点

### 1. 正確性・バグ（最重要）

- ロジックの誤り。空入力・極端に長い入力・マルチバイト・サロゲートペア・不正形式の見落とし。
- `any` の濫用、型の誤り。
- DOM 操作の null チェック漏れ、イベントリスナーの二重登録。

### 2. サーバー通信（違反は重大指摘）

- `fetch` / `XMLHttpRequest` / `WebSocket` / `navigator.sendBeacon` / 外部の `<script src>` `<img src>` が無いか。`Grep` で確認する。

### 3. セキュリティ

- `innerHTML` / `insertAdjacentHTML` / `set:html` にユーザー入力が入っていないか。HTML を生成する必要がある場合は `dompurify` でサニタイズされているか。
- `set:html` に渡す文字列が開発者管理の固定リテラルだけか（辞書の `introHtml` 等）。

### 4. 規約準拠

- ロジックが `src/lib/tools/<slug>.ts` に分離され、ページの `<script>` に直接書かれていないか。
- ロジック層に UI 文言が入っていないか。
- UI文言・コメントが日本語、識別子が英語か。
- React / Vue / Svelte を持ち込んでいないか。
- ja / en の辞書とラッパーが両方あるか。en が日本語のままになっていないか。
- `tools.ts` に `category` 込みで ja / en 登録されているか。カテゴリ表記が既存と揃っているか。

### 5. SEO・レスポンシブ

- `Layout` でラップされ、ページ専用の `title` / `description` があるか（`tools.ts` の説明の使い回しでないか）。
- `<h1>` が1つだけか。関連ツールへの内部リンクがあるか。
- 375px 前後で崩れなさそうか、タップ領域が十分か。マークアップと CSS から判断し、断定できないときは「断定できない」と書く。

### 6. 簡潔性

- 既存ユーティリティ・他ツールとの重複。使われていないコード。先回りした過剰な抽象化。
- 3行程度の重複は許容。無理な共通化で読みにくくなっていないかも見る。

## 報告フォーマット

日本語で、重大度順（バグ・セキュリティ・サーバー通信 ＞ 規約違反 ＞ 簡潔性の提案）に並べる。

```
### 指摘1 [重大 / 中 / 軽微]
- 場所: src/lib/tools/xxx.ts:42
- 問題: （何が問題か）
- 失敗シナリオ: （どんな入力・状況で何が起きるか）
- 修正案: （一言。コードは書かない）
```

- 問題が無かった観点も「問題なし」と書く（何を確認したか分かるように）。
- 推測で指摘しない。確認できたことと、確認できなかったことを分けて書く。
