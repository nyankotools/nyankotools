# 07. Qwen3.6 35B-A3B の運用ヒントと環境メモ

## 環境メモ（2026-09-19 時点で確認した事実）

| 項目                         | 内容                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------- |
| opencode の設定              | `C:\Users\zeit1\.config\opencode\opencode.jsonc`（ユーザー全体の設定）        |
| 接続先                       | `ollama` プロバイダ。`@ai-sdk/openai-compatible`、`http://localhost:11434/v1` |
| Ollama のモデル保存先        | `D:\OllamaModels`（環境変数 `OLLAMA_MODELS`）                                 |
| Ollama のバージョン          | 0.34.2                                                                        |
| 使うモデル                   | `qwen3.6:35b-a3b`（35.5B パラメータ、MoE、Q4_K_M、約22GB）                    |
| モデルの機能                 | completion / vision / tools / thinking                                        |
| モデル本来の最大コンテキスト | 262144                                                                        |
| 32k 版                       | Ollama に `qwen36-32k` がある（`num_ctx 32768` を焼き込んだ派生モデル）       |

opencode.jsonc には `qwen3.6:35b-a3b` が登録されているが、`qwen36-32k` は登録されていない（確認時点）。

### コンテキスト長の注意

- opencode は Ollama の OpenAI 互換エンドポイント（`/v1`）経由で接続している。**このエンドポイントからはリクエストごとに `num_ctx` を指定できない。** 実際に使われるコンテキスト長は、Ollama 側のモデル設定（Modelfile の `PARAMETER num_ctx`）か Ollama のデフォルトで決まる。
- `qwen3.6:35b-a3b` の Modelfile には `num_ctx` の指定が無い。つまり Ollama のデフォルトが使われる。デフォルト値は環境依存なので、**モデルをロードした状態で `ollama ps` を実行し、`CONTEXT` 列で実際の値を確認する。**
- opencode 自身のシステムプロンプトとツール定義だけでも数千トークンを消費する。コンテキストが小さいと、会話の前半（この文書の読み込み内容を含む）が黙って切り捨てられ、指示を忘れたような挙動になる。
- 症状の例: 直前に読んだファイルの内容を忘れる、`AGENTS.md` の禁止事項を守らなくなる、ツール呼び出しの形式が崩れる。
- 対処の選択肢（ユーザーが判断する。ローカルLLM側で設定ファイルを書き換えない）:
  1. opencode.jsonc の `models` に `qwen36-32k` を追加して、そちらを使う。
  2. Ollama の `OLLAMA_CONTEXT_LENGTH` 環境変数で既定値を上げる。
- どちらもメモリ（VRAM / RAM）を消費する。上げすぎるとオフロードが増えて遅くなる。

## 使い方のコツ

### タスクの切り方

- **1ターン1タスク・1ファイル。** 「ツールを丸ごと作って」ではなく、`02-add-tool-recipe.md` の表の1行ずつ進める。
- 1つ終わるたびに型チェック・lint を通し、問題があればその場で直す。
- 長い出力（100行を超えるファイル全文の再掲など）を避ける。編集は差分単位で行う。

### 書く前に読む

- 新しいファイルを作る前に、参照実装を**必ず開いて読む**。記憶や推測で雛形を書かない。
- import パス・関数名・ファイル名は、`Glob` / `Grep` で実在を確認してから書く。
- 迷ったら、憶測で埋めずにユーザーへ質問する。

### ツール呼び出しが壊れたとき

- 引数の JSON が壊れる、ファイル編集が失敗する、といったときは、**同じ引数で繰り返さない。**
- 対象を小さくして（1箇所ずつ）やり直す。編集の一致に失敗するなら、対象箇所を読み直して、周辺の数行ごと指定する。
- 3回続けて失敗したら、状況（実行したこと、エラー）をユーザーに報告して止まる。

### 思考（thinking）について

- このモデルは thinking 機能を持つ。複雑な設計判断（辞書の構造、テストの観点出しなど）では十分に考えてよい。
- 単純な編集（文言の差し替え、1行の修正）では長く考え込まず、すぐ実行する。

### 完了報告

- 「何をしたか」だけでなく、**実行したコマンドとその結果**を必ず書く（例: `pnpm exec astro check` → エラー0件）。
- 実行していない確認は「未実施」と明記する。実行していないのに「通った」と書かない。
- 触ったファイルを列挙する。`handoff.md` にも反映する。
